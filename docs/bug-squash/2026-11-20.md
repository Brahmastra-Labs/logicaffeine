# Bug squash, 2026-11-20: `logicaffeine_base`

The first daily bug-squash session. One section of the codebase a day, bugs found by reading, each one proved
by a test that fails on `main` before it is fixed. This file is the session's scratch pad and travels with the PR.

**Section:** `crates/logicaffeine_base`, the foundation crate (47 modules, about 47,000 lines, no internal
dependencies). Every other crate builds on it, so a bug here leaks everywhere.

**Base:** `main` at `fa0aaf6f`. **Branch:** `bugsquash/2026-11-20-base`.

**How the bugs were found.** Four read-only reviews ran in parallel, one per module group (time, money and units,
codecs and hashes, core structures, exact arithmetic). Each reported candidates with a concrete input. Every
candidate below was then re-read in the source by hand before a test was written, and one reviewer suggestion
(dropping fraction digits in `parse_duration`) was replaced with an exact method after the hand check showed it
could still round wrong for days, hours and minutes.

## Choices worth a second look

* **#4, a byte shift of 8 or more gives 0.** Every scalar `WordN` shift in `word.rs` takes the count modulo the
  width (x86 scalar `shr`), but a per-lane SIMD shift (`psrlw`, NEON `ushr`) clears the lane. `shr_bytes`
  models the SIMD one (its doc is the high-nibble extract `v >> 4`), so it now clears. If the language should
  take the count mod 8 instead, it is a one-word change to `wrapping_shr`, and the tests say which.
* **#10 keeps the two-double division for ordinary terms on purpose.** Its doc contrasts it with
  `rational_to_f64_nearest`, and other crates may compare against its current values. Only the non-finite case
  changes.

## Found, not fixed today (for Collin)

* **`exact_real.rs`, `ExactReal::exp`:** `exp(log x)` collapses to `x` without checking `x > 0`, so
  `exactExp(exactLn(0 - exactPi()))` prints `-π` where a domain error belongs. The fix needs a sign check on the
  log's argument that terminates on every form, which wants a careful look rather than a quick one.
* **`temporal.rs`, `from_local`:** its doc says a DST gap returns "the boundary instants". It returns the local
  time shifted by the gap (New York 2024-03-10 02:30 gives 06:30Z and 07:30Z, not 07:00Z). Either the doc or the
  code should change, which is a semantics call.
* **`temporal.rs`, `date_add_span`:** `days_since_epoch + 719468` overflows near `i32::MAX`. Only reachable at the
  edge of the `i32` day range.
* **`describe.rs`, `read_uvarint`:** accepts a 10th byte up to `0x7f` and drops its high bits, where the doc
  says an overflowing encoding is `None`. It cannot panic.
* **`shrBytes16` callers truncate the LOGOS count:** `builtins.rs`, `word_rt::shr_bytes16` and the wasm host's
  `logos_rt_lanes_shr_bytes` all pass `count as u32`, so `i64::MIN` arrives as 0 (the lanes come back
  unchanged) and `2^32 + 4` arrives as 4. A saturating conversion (`u32::try_from(count).unwrap_or(u32::MAX)`)
  at the three call sites would make every out-of-range count clear the lanes, as fix 4 does inside the
  crate. It is in `logicaffeine_compile` and `logicaffeine_system`, outside today's section.
* **`cm` mixer, `Mixer2::with_settling(0, _)`:** would divide by zero, but every caller passes a constant.
* **`gf256::solve`:** silently truncates when `b` is shorter than `a`, against its documented precondition.

## Proof

* **Red on `main`.** The new tests were copied onto an untouched `main` (`fa0aaf6f`) and run there: 33 of them fail,
  at least one for every fix but `falling`. The others are guards that hold on both sides (inputs the fixes must not change). The
  `falling` test cannot be compiled against `main`, where the function returns an `i64`, and the
  `add_business_days` test reaches a helper that `main` lacks (stood in by `main`'s own `n.abs()` for the check).
* **Green here.** `cargo nextest run --cargo-profile test-opt -p logicaffeine-base`: 979 tests, 979 passed.
* **Found while proving.** Two `to_f64` tests passed on `main` because `Rational::new` reduced their huge terms to
  small ones before the conversion ever saw them. Their numerators now end in 1, so they stay huge and fail on `main`.
